① 登记交叉校验（硬性）：规则由「质检标准」页的核查明细驱动
这条校验不是硬编码，而是运行时从「质检标准 → 流程&操作完整性」的核查明细文本里解析出来的。模板是：
在回邮数据中，<动作描述>，在<登记列名>中，显示“是” （动作描述里允许出现「；、，」，例如「客服承认 X；或者顾客反馈 Y」；「在<登记列名>中」前面的逗号可以省略）
  • 登记列名自动对应到上传表四列：退款登记 → 是否有退款登记；问题反馈 → 是否有问题反馈；补件 / 补发 → 是否有补件；检查流程 / 流程操作 → 是否需要检查流程操作。当前标准的核查明细只有「退款登记」「问题反馈」两条——补件条已被删除，因此不再校验「是否有补件」。
  • 期望值：写「是」就要求该列为「是」；写「否 / 无 / 不…」则要求为「否」。登记列空白或者填「否」，都算不一致。
  • 删掉某一条 → 该条校验自动取消；整段里不再出现「回邮数据」字样 → 交叉校验整体停用（保存标准时会提示已识别几条规则）。
  • 动作描述先匹配概念词库（见下表）；出现未登记的新概念时，自动降级为「条款实义词命中」兜底（中文二元组 / 英文词 ≥ 2 个命中即算）。
概念要求登记的列识别范围命中的写法（多语种）
客服答应顾客退款 / 已办理退款是否有退款登记 = 是客服回邮have processed / issued / initiated a refund；we have refunded；we will / can / would process a full or partial refund；rimborsato / provvederemo a rimborsare；Rückerstattung veranlasst / bearbeitet；nous vous avons remboursé；hemos procesado el reembolso；中文「已为您办理退款」「退款已处理 / 到账」「会 / 将 / 尽快 / 愿意 / 答应 + 退款」…
客服承认「描述不符 / 页面误导 / listing 问题」是否有问题反馈 = 是客服回邮not as described；listing was misleading / inaccurate；描述不符 / 与商品描述不一致 / 页面描述有误 / 页面误导 / listing 问题；non conforme alla descrizione；nicht wie beschrieben；description incorrecte；no coincide con la descripción…
顾客反馈「产品存在质量问题 / 收到产品不同相关内容 / 描述不符」是否有问题反馈 = 是顾客来信质量问题 / 有缺陷 / 瑕疵 / 损坏 / 破损 / 无法使用 / 与描述不符；difettoso / danneggiato / guasto / non funziona / non conforme alla descrizione；defekt / beschädigt / kaputt / nicht wie beschrieben；défectueux / ne fonctionne pas；defectuoso / dañado / no es como se describe…（条件句、否定句、「顾客自己买错」不算）
语境护栏：命中必须落在「干净的小句」里才算数
先取命中所在的单个小句（以 。！？；;.!? 和换行 为界），只要这个小句里出现条件、选择、待确认、推测语境，这条命中就被拦下、不算承诺：
  • 条件：如果 / 若 / 假如 / 万一 / 一旦 / 如需 / 无法解决 / 在…情况下；if / in case / qualora / se / wenn / falls / si / en caso…
  • 选择：或 / 或者 / 还是 / 替代方案 / 可选；either / or / alternative / option / oder / o bien / au cas…
  • 待确认：是否可以接受 / 请您确认 / 这样可以吗 / 您觉得如何；would that be acceptable / do you accept / acceptab / d’accordo / accetta…
  • 推测：might be / maybe / possibly / perhaps…
另外两条（2026-10-16 起）：
  • 疑问句 / 询问顾客不算承诺：命中所在的小句是疑问句（以 ？/? 结尾），或以「请问 / 能否 / 可否 / 是否 / 能不能 / 可不可以 / 您是否需要…」开头时，不算「答应退款」。
  • AZ 豁免：回邮（含顾客来信）出现亚马逊 A-to-z 索赔表述（A-to-z / A2Z / AZ 索赔 / 亚马逊索赔…）时，「是否有退款登记」填「是」或空白都算一致。
举例（判为「未承诺」，不要求登记）： 「如果问题仍无法解决，您无需退货，我们可以为您重新发货或直接退款」（条件 + 选择） 「您是否可以将商品保留，我们为您办理 35% 的部分退款」（待确认） 「Se riusciremo a intercettare il pacco, provvederemo al rimborso」（意语条件句） 对照（判为「已承诺」，要求登记）：We will process a full refund within 3 business days.
② 遗漏跟进核查（硬性）：让顾客等待后必须再发一封邮件
  1. 按会话顺序拆出每一封邮件，找出所有「客服回邮」中命中「让顾客等待」话术的邮件（顾客来信、亚马逊系统来信不算）。
  2. 逐封核对：这一封之后只要还有任何一封客服回邮 → 视为已跟进（不看那封写了什么、不看有没有真正解决、不设时间上限）；只要有一封之后再无客服回邮 → 判遗漏跟进。
  3. 出现遗漏时再套用「确认退款除外」，三种情况任一命中即豁免：本次会话任一回邮命中退款承诺 / 上传表「是否有退款登记」= 是 / 造成遗漏的那封等待邮正文里含退款字样（refund / rimbors / Erstattung / rembours / reembols / 退款 / 退回货款…）。
「让顾客等待」话术库（无显式等待词就不触发）
英：please / kindly wait · allow us · bear with us · give us · wait for N days / hours / weeks 意：attendere N · la preghiamo di attendere · pazientare 德：warten Sie N · bitte warten / Geduld · haben Sie Geduld · in N Tagen / Stunden / Wochen 法：patienter / patientez N · veuillez patienter 西：espere N · por favor espere · tenga paciencia · en N días / horas / semanas 中：请您耐心等待 · 请稍等 · 稍等 N · 等待 N 天 / 小时 / 工作日 / 周 · 请给我们 N
两个已知边界（目前刻意不判，避免误伤）：① 后续那封跟进邮件的内容不校验——哪怕完全没提等待事项、隔了 20 天也算已跟进；② 不检查发送状态——带 [发送失败] 的等待邮与跟进邮都照常参与判定。

  • ML_PERSONAL 区分大小写：必须是 Dear / Hi / Hello / Gentile / Caro / Egregio / Sehr geehrte / Cher / Estimado 后紧跟大写开头的人名，或中文「尊敬的 / 亲爱的 + 先生 / 女士 / 小姐」。泛称（如 Gentile acquirente）不算。
  • 主动收尾用 ML_CONTACT（anything else / feel free / don’t hesitate / 请随时联系我们 …），不要与方案维度的 ML_PROACTIVE（预防 / 建议 / 风险）混用。
  • 并行扫描（只记 issue、不改分）：正文出现两次「please provide / could you provide / please send」→ 追加「可能存在重复索要信息」。
本维度的档位分值目前是引擎内置常量（标准页只写「优秀 / 达标 / 不达标」，引擎另有一个更细的中间档），在标准页改分值不会改变本维度实际得分。

知识类型对分数的影响说明
好案例 / 质检知识（can-do）保底到该维度满分的 80%，并把该维度等级写成「达标」即「判分服从 SOP」：命中可推广做法时，该维度不会低于达标线。例外：该维度存在硬性不达标（流程维度登记不一致 / 遗漏跟进）时跳过保底。
不好案例 / 漏检知识（case-bad / missed）扣掉该维度满分的 40%（至少扣 5 分），并判「不达标」命中即写入 issue：「违反SOP（知识库）：<标题>」。
参考案例（reference-case）总分 -2，标记「参考案例」申诉通过后沉淀的样本，不参与达标 / 不达标统计。
知识项怎么算命中
  • 每个知识项自动提取「判分依据」：明确要求（core，含数字 + 时间单位、≥3 字中文、无中文但 ≥5 字母或多词的英文）+ 参考词（aux，同义扩展）。
  • 正向项（好案例 / 质检知识）：明确要求命中 ≥ 1 条即生效；没有明确要求时退化为参考词 ≥ 2。
  • 负向项（不好案例 / 漏检）：必须命中明确要求才生效（只有该项自身提取不到明确要求时，才退化为参考词 ≥ 3）。这条不对称规则是为了避免「退款 / 方案 / 替代」这类通用词把大批单据误判成不达标。
  • 适用维度可多选；勾了具体维度又勾「综合」时，以具体维度为准。
所以「质检明细」里可能看到分数与等级不匹配：例如某维度显示 40 分却写「达标」，那是好案例把等级直接写成了「达标」。遇到这种情况先查这条，再看申诉状态。
申诉怎么影响明细
申诉通过后，被勾选的维度会被改判为「达标」，issues 末尾追加「申诉审核通过，模块调整为达标」。因此可能出现「维度等级已达标，但问题说明里仍保留原不达标文案」——这是申诉痕迹，不是 bug。

8 · 「问题说明」怎么读（对应质检明细 → 详情）

打开详情时实时生成，与云端明细无关
明细详情里「各维度质检结果」表格的最后一列「问题说明」，按维度等级分三种模板：
维度等级区块标题内容
不达标问题原因（判定依据）【问题邮件】第 N 封 →【具体不达标内容】本维度所有 issue →【应达到的标准】引用「质检标准」页该维度的优秀档条款（截断到 180 字）。
问题邮件（实际回邮）定位到具体第几封客服回邮，并摘出命中的原文片段。
针对性优化方案（改写示例）按维度 + issue 关键词给的改写话术（流程维度会分别给「补登记」「补跟进」「写到账时间」三种建议）。
优秀优秀原因（符合标准）【优秀依据邮件】→【优秀原因】→【符合标准】（该维度优秀档条款）。
优秀依据（实际回邮）实际命中的邮件与片段。
达标符合标准 / 达标理由有 issue 就列 issue，没 issue 就给该维度的通用达标理由。
邮件级定位格式
第3封（客服回邮 · 发送成功 · 2026-08-05 13:59:40）：「…命中的原文片段…」
会话按「收起」拆封；证据优先取客服回邮、优先命中该维度关键词；本单若纳入过亚马逊系统来信，证据定位也会把它算进去，避免出现「未定位到具体邮件」。
「操作完整性」原因行
流程维度不达标、且成因是登记字段时，会在这段「问题说明」的标题下方、问题邮件行上方多出一行操作完整性：原因：…（详见「3 · 流程&操作完整性」）。
「问题说明」是纯展示层：只改文案或证据定位方式时，不需要重跑云端明细；只有判分逻辑或质检标准改变时才需要全量重跑。

9 · 同步机制与已知边界

改标准 / 改逻辑之后会发生什么
三条同步链路
触发动作结果
在「质检标准」页点「保存标准」标准写入云端并生成新的标准指纹 → 立即全量重跑所有明细（申诉保留），明细按新标准刷新；流程维度的核查规则也同步重新解析。提示会回显「已识别 N 条『回邮数据 × 登记列』核查规则」，识别不到会明确警告交叉校验已停用。
判分逻辑升级（版本号变化）页面载入云端状态时发现版本落后，自动按最新逻辑重跑全部明细并保留申诉。
重新上传数据按当前全局标准全量重算；「清空后上传 / 累计上传」只影响是否保留旧数据。
看数据是否新鲜
不要看云端记录的 updated_at，要看 判分逻辑版本号 与 标准指纹：两者任一与页面不一致，页面打开时会自动重跑一次（表现是加载稍慢），这属于正常自愈，不是重复质检。本页当前的版本 / 指纹 / 明细条数：正在读取…。
本说明书的哪些部分会跟着变
改动来源本页的反应
「质检标准」页改分值 / 等级区间即时变：目录与各节标题的满分、0 节流程图分值、档位表、总分合计、等级阈值；全量明细同时按新标准重跑，各节落点统计随之刷新。
「质检知识库」增删 / 修改条目即时变：第 7 节的「当前知识库构成」与落点统计；明细会重跑，保底 / 扣分条数同步刷新。
重传或新增明细数据即时变：全部落点统计按当前明细重算。
改动判分逻辑（代码）需要重新部署本页：判定顺序、词库明细、豁免规则这些文字是照着代码写的，代码改了要同步改文字；分值若一并提为常量，本页会自动跟随。
方案 / 技巧 / 态度的档位分值不会跟着标准页变：这三项的分值是引擎内置常量（比标准页多一个中间档），改标准页得分不影响实际判分，需改造判分函数。
已知边界（当前刻意不判，收到反馈再评估）
  1. 遗漏跟进的跟进内容不校验：等待后只要再有一封客服回邮即算跟进，不看写了什么、不设时限。
  2. 不检查发送状态：带 [发送失败] 的邮件照常参与判定。
  3. 「没有客服回邮」的判定依赖上传数据里带 [发送成功] / [发送失败] / [已撤回] 标记：若换用不带这些标记的导出格式，整批单子会被判「无法质检」，届时需要调整判定方式。
  4. 方案合理性的四种「方案质量问题」无正则判定，依赖人工申诉。
  5. 登记列依赖上传表：早期批次三列登记全空会让单子因「退款登记空白」判流程不达标，当前为 0 条，需要重传带齐四列登记字段的完整表才能消除。
  6. 本说明书里的分值、比例与阈值均取自「质检标准」页与引擎常量，落点统计取自当前明细；本页每次打开都会重算，不需要人工更新数字。判定顺序与词库明细属于代码逻辑，只随代码版本变化。
